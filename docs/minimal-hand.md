# 攻方の持ち駒を最低限にする案の検証

2026-11-15 に検討し、同日、一括変換プログラムを追加した。採用する変換は案A（余りの駒を玉方に渡す）。

## 背景

問題データ（やねうら王 2020年クリスマスプレゼントの実戦詰将棋）は、コンピュータ同士の対局の終盤（元の対局で110手目前後）を切り出したものである。
そのため攻方の持ち駒が多く、王手を続けるだけで詰んでしまう問題が混ざる。

- 攻方の持ち駒は平均6.3〜6.4枚（中央値6枚）。10枚以上の問題が13〜16%ある（各手数20巻＝約2万問を集計）。
- 例：7手詰 577-171 は、攻方の持ち駒が「飛 角 金 銀2 桂2 香 歩7」の16枚。玉方は持ち駒なし。
- なお、データの読み込みの誤りではない。盤上の駒と持ち駒を合わせて全問40枚になることを、各手数3巻（約1万5千問）で確認した。

## 案

収録されている正解手順をたどり、攻方が最初に持っている必要がある最低限の持ち駒だけを残す。
手順の途中で取った駒を打つ分は、最初の持ち駒には数えない。余った駒の扱いで2案を比べた。

- **案A**：余りの駒を玉方の持ち駒に加える（作られた詰将棋の「残りの駒は玉方が持つ」流儀。盤と駒台で40枚のまま）
- **案B**：余りの駒を取り除く（盤と駒台で40枚未満になる。エンジンはこの局面も受け付ける）

どちらの案でも、検証で詰まなくなった局面は除く（または元の局面に戻す）前提である。

| 3手詰 | 6.4枚 | 1.13枚 | 21.9% | 43.1% | 35.0% | 97.2% |
| 5手詰 | 6.4枚 | 1.54枚 | 14.1% | 36.0% | 49.9% | 96.8% |
| 7手詰 | 6.3枚 | 1.88枚 | 10.0% | 28.3% | 61.7% | 95.8% |
| 9手詰 | 6.3枚 | 2.11枚 | 7.9% | 24.6% | 67.5% | 94.9% |
| 11手詰 | 6.3枚 | 2.33枚 | 5.9% | 20.8% | 73.3% | 94.2% |

## 結果2：減らしても N 手で詰むか

`docs/minimal-hand/minhand-verify.mjs` で、各手数の321巻の先頭30問を調べた。
ブラウザと同じ WASM 版のエンジン（つようら王11mini、1スレッド、置換表16MB）で攻方の手番から3秒探索し、`score mate +k`（k ≤ N）が出た数を数えた。

| 手数 | 元のまま | 案A：余りを玉方に渡す | 案B：余りを取り除く |
|---|---|---|---|
| 3手詰 | 30/30（平均9ms） | 27/30（304ms） | 28/30（203ms） |
| 5手詰 | 30/30（68ms） | 27/30（236ms） | 28/30（136ms） |
| 7手詰 | 30/30（400ms） | 22/30（719ms） | 24/30（555ms） |
| 9手詰 | 28/30（1941ms） | 21/30（1656ms） | 22/30（1547ms） |
| 11手詰 | 25/30（2841ms） | 21/30（2616ms） | 24/30（2409ms） |

- 「元のまま」でも9・11手詰で取りこぼしがある。3秒の通常探索では長い詰みを見つけきれないためで、案A・B の数字にも同じ取りこぼしが含まれる。
- 残る割合はおおむね、3〜5手詰で約9割、7〜11手詰で約7〜8割。

## 分かったこと

- **収録されている手順は、玉方の応手を1通りだけたどった「本手順」である。**
  玉方が別の応手（変化）を選んだときは、本手順では使わない持ち駒が必要なことがある。
  例：3手詰 `l2+R3nl/2+S1g1k2/4+b1pP1/4p1Spp/Pp4N2/3+b1PG1P/1P2+r1P2/6S2/5GKNL w S2Pgnl5p 110`（解 `5g3g 4i4h 6f4h`）。
  本手順では駒を一度も打たないが、持ち駒を0枚にすると詰まなくなる。
  したがって、**案Bでも本手順だけから求めた持ち駒では足りないことがあり、どちらの案もエンジンでの検証が必要**。
- **案Aでは、玉方が受け取った駒で合駒できるようになる**ため、案Bより少し多く詰まなくなる。
  一方で、合駒を考える場面が増えるので、問題としては案Aのほうが面白くなると考えられる。
- **案Aでは、収録解がそのまま正解とは限らない**（玉方が合駒して別の手順になることがある）。
  最短解は、検証の探索でエンジンが出した読み筋に置き換える必要がある。
- **手数が N より短くなることはない。** 攻方の打てる駒は減り、玉方の受けの手段は増えるだけなので、「N 手以内の詰みが見つかった」ならちょうど N 手詰である。

## 変換方式の選択肢

1. **出題時にアプリ内で変換する**：出題のたびに案Aの局面を作り、エンジンで1〜2秒探索して検証する。詰みが見つからなければ元の局面で出題する。
   データの作り直しも事前の一括処理も要らない。代わりに出題時に1〜2秒待ち、9・11手詰では元の局面に戻ることが多い。
2. **事前に一括変換して R2 のデータを差し替える**：追加した一括処理プログラムは公式やねうら王詰み証明エンジンを複数プロセスで動かし、証明できた問題と新しい詰み手順だけを保存する。
   全件の処理時間は問題ごとの探索時間に左右されるため、全データでの実測後に決める。
3. **持ち駒の枚数で絞るだけ**：「攻方の持ち駒 N 枚以下」を出題設定に足す。最も簡単だが、「持ち駒は少ないのに簡単」な問題は残る。

## 再現手順

```bash
npm run fetch:problems                                   # 問題データを .cache/shogimate に取得
python3 docs/minimal-hand/minhand.py                     # 結果1
node docs/minimal-hand/minhand-verify.mjs "$PWD" 30 3000 # 結果2（10分前後）
SHOWFAIL=1 BOOKS=mate3 node docs/minimal-hand/minhand-verify.mjs "$PWD" 30 3000  # 詰まなかった局面を表示
```

📝 Node で Emscripten の pthread 版を動かすときは、待ち受け中もタイマーなどでイベントループを維持すること。
探索スレッド（worker）はイベントループを維持しないので、Node が探索の途中で終了してしまう（スクリプトでは `setInterval` で対処している）。

## 一括処理プログラム

[`scripts/filter-minimal-hand.py`](../../scripts/filter-minimal-hand.py) は、入力フォルダの階層とファイル名を保ったまま、証明された Yes の棋譜だけを別の出力先に保存する。出力の各行は、攻方の余り駒を玉方に渡した初期SFENと、エンジンが証明した詰み手順で構成する。No、時間切れなどで未解決の局面、不正な棋譜は出力しない。

事前に問題データと公式エンジンを用意し、リポジトリ直下から実行する。エンジン取得・ビルドには公式GitHubの固定コミットを使う。

```bash
npm run fetch:problems
npm run prepare:mate-engine
npm run filter:minimal-hand -- --engine "$PWD/.cache/research/YaneuraOu/source/YaneuraOu-by-gcc"
```

- 入力：`.cache/shogimate/public/data/mate{3,5,7,9,11}/`
- 出力：`.cache/minimal-hand/public/data/mate{3,5,7,9,11}/`
- 既定で CPU 数と空きメモリから同時実行数を決める。`--workers` で指定でき、各エンジンの探索メモリは `--hash-mb`（既定4096MB）。
- 各局面の探索上限は既定30秒。`--timeout-ms` で変更できる。未解決はYesに含めず、件数を処理結果に記録する。
- エンジン終了や応答切れがあった局面は、エンジンを再起動して既定2回まで再試行する。`--retries` で回数を変更できる。再試行後も失敗したファイルは完了扱いにせず、同じ設定で再実行すると再処理する。
- 完了済みファイルの状態を `.cache/minimal-hand/state/` に保存し、再実行時は入力と設定に変更がないファイルを飛ばす。
- 少量での試行には `--limit-files 1 --limit-records 10` を使う。試行時は完了状態を保存しない。

全件の出力を本番データへ反映する前に、No・未解決・処理エラーの件数を集計し、未解決が残った場合は時間上限を増やして再処理する。既定では未解決棋譜は出力されない。

本番へ反映するときは、出力から索引を作り直し（`npm run build:index`）、同じ出力を R2 に上げる（`npm run upload:problems`、既定の入力が `.cache/minimal-hand/public/data`）。
問題を除くと行番号（問題 ID の一部）がずれるので、解答履歴（KV）もリセットする。

## 正解手順の作り直し（玉方の応手をアプリに合わせる）

2026-11-17 に追加した。上の変換で保存した手順は、詰み専用エンジン（df-pn）がたまたま証明した1本である。
同じ手数で詰む応手が複数あると、df-pn はその中から1つを任意に選ぶ。そのため、アプリの玉方（mini）が金合いする場面で、正解手順は歩合いになることがある。

- 計測（各手数30問、アプリと同じ WASM 版の mini、4スレッド、応手時間もアプリと同じ）：収録手順の応手と mini の応手が一致しない問題は、3手詰で5/30、7手詰で12/30、9手詰で17/30。
  不一致の61手はすべて同じ手数で詰む応手で、収録手順より長く粘る応手は無かった（収録手順は正しいが、手の選び方が mini と違う）。

[`scripts/regen-solutions.py`](../scripts/regen-solutions.py) は収録手順をたどり、合法手が2つ以上ある玉方の手番ごとに、ネイティブ版の mini（アプリと同じソースと評価関数）に応手を選ばせる。
mini の応手が収録手順と違えば、その後も残りの手数ちょうどで詰むことを詰み専用エンジンで確かめ、その手順に差し替える。確かめられなければ収録手順の応手を残す。
手数は必ず元の N 手のままになる。同じ初期局面（盤・手番・持ち駒が同じ）の重複は、最初の1つだけを残す（304件）。

```bash
npm run prepare:native-mini   # ネイティブ版 mini をビルド（.cache/research/mini-native）
npm run prepare:mate-engine   # 公式の詰み専用エンジン（未ビルドなら）
npm run regen:solutions       # 入力 .cache/minimal-hand/public/data → 出力 .cache/regen-solutions/public/data
```

- mini は1スレッド・読む局面数を固定（`--nodes`、既定10万）にし、探索のたびに置換表を消す。同じ局面なら毎回同じ手を返す。
- 3〜11手詰の問題をまとめてシャッフルし、1問ずつ配る。軽い問題と重い問題が常に混ざって流れる。
- 並列数は既定で論理コア数の2倍。i7-13700K（論理24コア）で4万問を流した結果は、24並列が194問/秒（CPU 60%）、32並列が220問/秒（85%）、48並列が230問/秒（99%）、64並列が222問/秒（100%）。
  軽い局面ではエンジンとの往復の待ち時間が長いので、論理コア数と同じ並列数では CPU が遊ぶ。全410万問で約5時間。
- 1問終わるごとに `.cache/regen-solutions/state/journal-<設定>.jsonl` に追記する。中断しても、同じ設定で再実行すれば続きから処理する。全問が終わると出力と集計（`summary.json`）を書く。
- 試行には `--limit 1000 --output /tmp/regen-trial` を使う（出力ファイルは書かない）。
- 試行（3.5万問）では39%の問題の手順が変わった。玉方の手番は、合法手が1つが42,132回、mini と同じが41,909回、差し替えが17,010回、mini の応手のほうが早く詰むので収録の応手を残したのが62回。
  変わった問題500問を調べ、全手が合法で、攻方の手がすべて王手で、最後に詰むことを確かめた。
- 同じ試行から各手数40問を選び、アプリと同じ WASM 版の mini（4スレッド、時間で区切る）の応手と比べた。全応手が一致した問題の数は次のとおり。
  残る不一致は、どれも同じ手数で詰む応手だった。アプリは4スレッド・時間で区切り、作り直しは1スレッド・局面数で区切るので、同じ手数で詰む応手の中で選ぶ手が分かれることがある。

  | 手数 | 作り直す前 | 作り直した後 |
  |---|---|---|
  | 3手詰 | 36/40 | 40/40 |
  | 5手詰 | 30/40 | 38/40 |
  | 7手詰 | 21/40 | 32/40 |
  | 9手詰 | 19/40 | 34/40 |
  | 11手詰 | 18/40 | 32/40 |

反映するときは、出力から索引を作り（`node scripts/build-problem-index.mjs .cache/regen-solutions/public/data public/problems-index.json`）、同じ出力を R2 に上げる（`PROBLEMS_DIR=.cache/regen-solutions/public/data npm run upload:problems`）。
重複を除いたので行番号（問題 ID の一部）がずれる。解答履歴（KV）もリセットする。
