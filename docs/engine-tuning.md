# 玉方エンジンの速さの検討

2026-11-17 に、玉方の探索（詰みの判定）を速くできないかを測った。結果と決めたことを残す。

## 背景

攻方が指すと、玉方のエンジン（つようら王11mini）が `go movetime` で探索し、`score mate` が出れば「詰みあり」として続ける（`src/game/session.ts`）。
考える時間は、問題の残り手数だけで決めている（`defenderMovetimeMs`）。
詰みがあるとエンジンはすぐ返すので、応手を見せるまでの時間もこの値にそろえ、待ち時間で正誤が分からないようにしている。

| 攻方が指した後の残り手数 | 考える時間 | 主な場面 |
|---|---|---|
| 4手以下 | 300ms | 3・5手詰の全部、7手詰の2手目以降 |
| 6手 | 500ms | 7手詰の初手 |
| 8手 | 1000ms | 9手詰の初手、11手詰の3手目 |
| 10手 | 1500ms | 11手詰の初手 |

時間内に詰みを見つけられないと、本当は正しい手でも「詰みを逃した」とみなす（猶予で取り消されることもある）。

## 測り方

- PC（24コア）の Node で、ブラウザと同じ WASM 版のエンジンを動かした。スマホでは測っていない。
- 問題は `.cache/minimal-hand/public/data` の各手数 002 巻から、1巻50問ずつ200問。
- 収録解どおりに進めた局面で、玉方の手番から探索し、`score mate` が出るまでの時間を測った。
  - 11手詰の玉方1手目（残り10手）と3手目（残り8手）、9手詰の玉方1手目（残り8手）。
  - 上限は6秒。それまでに出なければ「未発見」。
- 問題ごとに `isready` で置換表を空にした。問題の中の続けての探索は空にしない（アプリと同じ）。
- スクリプトは `docs/engine-tuning/` にある。

⚠ 置換表を空にしないで測ると、前の局面の結果が残るため、同じ設定でも中央値が3倍ほど変わった。
40問でそう測ったときは、スレッド数の効果が見えなかった。設定を比べるときは、必ず問題ごとに空にすること。

## 結果1：スレッド数と置換表（mini）

`node docs/engine-tuning/mini-tune.mjs "$PWD" <Threads> <USI_Hash> 200 <出力>` を12通り。
6つの設定を同時に動かしたので、4スレッドの数字は CPU の取り合いの分だけ少し悪く出ているかもしれない。

| 設定 | 残り10手：中央値 | 95% | 1500ms 以内に見つからない | 残り8手：1000ms 以内に見つからない |
|---|---|---|---|---|
| 1スレッド・16MB（元） | 1098ms | 5178ms | 66/200（33%） | 4/400 |
| 2スレッド・16MB | 695ms | 3560ms | 38/200（19%） | 4/400 |
| 4スレッド・16MB | 423ms | 2536ms | 21/200（11%） | 7/400 |
| 1スレッド・32MB | 1066ms | 4731ms | 67/200 | 5/400 |
| 2スレッド・32MB | 653ms | 3450ms | 40/200 | 1/400 |
| 4スレッド・32MB | 456ms | 2358ms | 23/200 | 2/400 |
| 1スレッド・64MB | 1005ms | 4511ms | 63/200 | 6/400 |
| 2スレッド・64MB | 668ms | 3569ms | 33/200 | 3/400 |
| 4スレッド・64MB | 385ms | 3206ms | 20/200 | 5/400 |
| 1スレッド・128MB | 1079ms | 5039ms | 66/200 | 4/400 |
| 2スレッド・128MB | 580ms | 2863ms | 33/200 | 2/400 |
| 4スレッド・128MB | 390ms | 2749ms | 21/200 | 1/400 |

- **スレッドを増やすと効く。** 4スレッドで、残り10手の見落としが33%から11%に減った。
- **置換表の大きさは効かない。** 16〜128MB で、はっきりした差はなかった。
- 残り6手以下は、1スレッドでも PC で最大300ms 未満だった（前に40問ずつ測った結果。残り4手以下は最大51ms）。

## 結果2：詰み専用エンジン（df-pn）

データの変換（`scripts/filter-minimal-hand.py`）に使っている公式やねうら王の詰将棋エンジン版を、WASM にビルドして測った。

### アプリで使うときの判定のしかた

このエンジンは「手番の側が詰ませる」局面しか扱えない。攻方が指した後の局面（玉方の手番）を渡すと、調べずに `checkmate nomate` を返す。
そこで、次のようにして判定した（`docs/engine-tuning/mate-bench.mjs`）。

1. 玉方の合法手を、mini エンジンの `moves` で並べる。
2. 応手ごとに、攻方の手番の局面で `go mate`（`DepthLimit` = 残り手数 − 1）を調べる。
3. すべての応手で詰めば詰み。1つでも `nomate`・`none`・`timeout` なら不詰（そこで打ち切る）。

### 結果（1スレッド、200問、結果1と同じ局面）

| 置換表 | 正しい手（600局面） | 正しい手の時間：中央値 / 95% / 最大 | 間違った王手で「判定できず」（`none`） | 間違った王手の時間：中央値 / 95% / 最大 |
|---|---|---|---|---|
| 16MB | 全件を詰みと判定 | 6 / 17 / 71ms | 10/398 | 7 / 71 / 191ms |
| 64MB | 全件を詰みと判定 | 6 / 20 / 64ms | 1/398 | 9 / 64 / 418ms |
| 256MB | 全件を詰みと判定 | 6 / 17 / 102ms | 0/398 | 7 / 61 / 683ms |

- 「間違った王手」は、収録解の初手以外で最初に見つかった王手。398件のうち26件は別の詰みがあり、正しく詰みと判定した。
- `none` はメモリ不足で結論が出なかったもの。置換表を大きくすると減る。
- 200問（約1000回の判定）が18秒で終わった。mini は同じ局面で数十分かかる。
- 結論：**正誤の判定を詰み専用エンジンに任せれば、手数によらず数十msで、見落としなく判定できる見込み**。

### ビルドのしかた

公式の Makefile がそのまま使える。`engine/build.sh mate`（`npm run build:engine -- mate`）にまとめた。
ソースは `npm run prepare:mate-engine` で取得したもの（`.cache/research/YaneuraOu`、コミット `2bc64b4`）を、ネイティブ版を消さないよう `engine/build/mate` にコピーし、パッチを当ててビルドする。

```bash
npm run prepare:mate-engine        # 公式ソースの取得（ネイティブ版のビルドも行う）
npm run build:engine -- mate       # public/engine/yaneuraou.mate.{js,wasm,worker.js}
```

- wasm は約600KB で、評価関数ファイルは要らない。
- パッチ（`engine/mate-engine-wasm.patch`）は2行だけ。
  - 探索の終了を100msごとに確かめていたのを1msごとにした。そのままだと、すぐ解ける局面でも1回に最低100msかかる。
  - 1ms 未満で解けると速度の計算が0で割るので、それを避けた（WASM では例外で止まる）。
- 公式の既定から2つ変えている。
  - 前もって作るスレッドの数（`PTHREAD_POOL_SIZE`）を32から4に。そのままだとブラウザで Worker を32個作る。
  - 書き出し名（`EXPORT_NAME`）を `YaneuraOuMate` に。mini と同じ `YaneuraOu` だと、ブラウザで両方を読み込めない。
- ⚠ 一部のファイルだけを `make normal` でビルドし直すと、`tournament` でビルドした残りと設定が食い違い、`go mate` が応答しなくなった。必ず `clean tournament` でビルドし直すこと。
- エンジンの既定値は `Threads 4`・`USI_Hash 1024` なので、使うときは必ず設定し直す。

## 結果3：手数の上限をなくす（遠回りの詰みも詰み）

アプリでは、最短でなくても詰めば成功にしている。結果2は `DepthLimit` を残り手数ちょうどにしていたので、遠回りの詰みを「詰まない」と判定していた。
そこで上限をゆるめて測り直した（`mate-bench.mjs` の最後の引数。`none` が上限なし、`+N` が残り手数 + N 手まで）。
正しい手（600局面）は、どの設定でも全件を詰みと判定し、最大でも約70msだった。違いが出たのは間違った王手（398件）。

| 手数の上限（置換表） | 遠回りで詰む | 詰まない | 判定できず（`none`） | 詰まないと分かるまで：中央値 / 95% / 最大 |
|---|---|---|---|---|
| 残り手数ちょうど（64MB） | 26 | 371 | 1 | 5 / 50 / 420ms |
| +2手（64MB） | 53 | 334 | 11 | 9 / 201 / 451ms |
| +4手（64MB） | 81 | 301 | 16 | 13 / 370 / 492ms |
| +8手（64MB） | 100 | 246 | 52 | 30 / 444 / 618ms |
| +16手（64MB） | 112 | 218 | 68 | 37 / 474 / 622ms |
| 上限なし（16MB） | 110 | 177 | 111 | 41 / 131 / 323ms |
| 上限なし（64MB） | 113 | 215 | 70 | 37 / 476 / 1516ms |
| 上限なし（256MB） | 117 | 238 | 43 | 36 / 1812 / 3472ms |

- 時間切れ（`timeout`、上限6秒）は1件もなかった。結論が出ないのは、どれもメモリ不足（`none`）。
- 上限付きの `nomate` は「その手数では詰まない」というだけで、もっと長い詰みが残っているかもしれない。遠回りでも成功という決まりと合うのは、上限なしだけ。

### 今の mini（4スレッド）との比較

同じ間違った王手の後を、mini で6秒まで探索した（`docs/engine-tuning/mini-wrong.mjs`。問題を5つに分けて並列に回した）。
「時間内」は今の考える時間（間違った王手の後は残り8・10手なので1000・1500ms）。

| 詰み専用エンジン（上限なし・64MB） | 件数 | mini が時間内に詰みと判定 | mini が6秒以内に詰みと判定 | mini が6秒でも見つけられない |
|---|---|---|---|---|
| 詰む（遠回り） | 113 | 32 | +27 | 54 |
| 詰まない（`nomate`） | 215 | 1 | +1 | 213 |
| 判定できず（`none`） | 70 | 0 | +1 | 69 |

- **遠回りの詰みの7割（113件中81件）を、mini は時間内に見落としていた。** mini が見つけた詰みは8〜24手。
- **`none` の局面は、mini でもほぼ詰みを見つけられない。** `none` を mini に任せても、今より悪くならない。
- 詰み専用エンジンが「詰まない」とした局面で、mini が詰みと読んだものが2件あった。王手でない手を含む詰みを読んだものとみられる（中身は未確認）。王手だけで詰ませる決まりでは、詰み専用エンジンの判定が正しい。

## 結果4：メモリ

2026-11-17 に、2つのエンジンを読み込んだときのメモリを測った。スマホでは測っていない。

### 起動直後（PC のヘッドレス Chrome、dev サーバー）

| 何が | 量 |
|---|---|
| Chrome 全体（PSS、子プロセスすべての合計） | 白紙ページで約330MB → アプリ起動後は約1,120MB（約+790MB） |
| そのうち、アプリのページの描画プロセス | 約750MB |
| mini の WASM メモリ | 461MB |
| 詰み専用エンジンの WASM メモリ | 275MB（最初の判定の後は330MB） |

- 増えた分は、ほぼすべて2つのエンジンの WASM メモリ。画面や JavaScript の分は数十MB しかない。
- ⚠ `performance.measureUserAgentSpecificMemory()` は約8.9GB と出た。WASM のメモリが確保しうる上限（`MAXIMUM_MEMORY` の4GB）を Worker ごとに数えているとみられ、実際の量の目安にならない。

### エンジンごとの内訳（Node、アプリと同じ設定。`docs/engine-tuning/wasm-memory.mjs`）

| エンジン | 読み込み直後 | `isready` の後 | 最初の探索の後 |
|---|---|---|---|
| mini・1スレッド | 128MB | 221MB | – |
| mini・4スレッド（今の設定） | 128MB | 461MB | 461MB |
| 詰み専用エンジン・置換表16MB | 132MB | 190MB | 245MB |
| 詰み専用エンジン・置換表64MB（今の設定） | 132MB | 229MB | 330MB |
| 詰み専用エンジン・置換表128MB | 132MB | 293MB | 422MB |

- **mini はスレッドを1本増やすごとに約80MB 増える。** 4スレッドにしたことで約240MB 増えた。
- WASM のメモリは一度増えると減らない。

### 使い続けたとき（`docs/engine-tuning/memory-soak.mjs`）

アプリと同じ使い方（問題の間で置換表を空にしない）で、11手詰と9手詰を200問ずつ判定した。

| 時点 | mini | 詰み専用エンジン | JS ヒープ |
|---|---|---|---|
| 起動後 | 461MB | 229MB | – |
| 50問後 | 461MB | 330MB | 6MB |
| 100〜400問後（判定5,537回） | 461MB | 330MB | 7MB |

- **増えるのは最初の判定の1回だけで、その後は増えない。** 最初の1問を判定できれば、必要なメモリはすべて確保できている。

### OOM になったら

自動では立ち直らない。

- **WASM の中でメモリが足りなくなった場合**：エンジンは止まる（`-fno-exceptions` なので強制終了）。返事が来ないので、60秒待ってから（`UsiEngine.sendAndWait` のタイムアウト）エラーを出す。「次の問題」を押しても、止まったエンジンをそのまま使うので直らない。ページの再読み込みが要る。
  上の結果から、使い続けてこれが起きることはまず無いと考えている。
- **ブラウザや OS がタブを落とした場合**：戻るとページが読み込み直される。解いた記録はサーバーと端末に残る。メモリが少ない端末で、裏に回したときに起きやすい。

### 減らすなら（未実施）

- mini を1スレッドに戻す（約240MB 減る）。4スレッドにしたのは詰みの見落としを減らすためだったが、今は正誤を詰み専用エンジンが判定するので、速さの利点はほとんど無い。
- 詰み専用エンジンの置換表を16MB にする（約85MB 減る）。ただし、間違った王手で「判定できず」が増える（398件中70件 → 111件）。
- エンジンが止まったら、エラーのときに2つのエンジンを作り直す。

使ってみて発熱やメモリ不足は出ていないので、今は何もしない。

## 決めたこと

- **mini を4スレッドにした**（`src/engine/EngineClient.ts`）。前もって作っておくスレッドの数（`PTHREAD_POOL_SIZE=4`、`engine/build.sh`）の範囲に収まる。ヘッドレス Chrome で11手詰を3問指し、応手が返ることを確かめた。スマホでは、電池の減りや発熱が増えるかもしれない。
- **置換表は16MBのまま**にした。大きくしても効果が見えなかったため。
- **考える時間は変えない。** 延ばして判定が良くなるのは9・11手詰の序盤だけで、そこは演出で待ち時間を隠せる長さではない。
- **正誤の判定を詰み専用エンジンに置き換えた**（`src/engine/MateClient.ts`、`src/game/session.ts`）。
  - 攻方が指したら、mini の探索と、詰み専用エンジンでの応手ごとの判定を同時に始める。持ち時間はどちらも今までの考える時間（`defenderMovetimeMs`）で、待ち時間は変わらない。
  - 詰み専用エンジンは `Threads 1`・`USI_Hash 64`・`DepthLimit 0`（上限なし）。256MB は `none` が減るが、詰まないと分かるまで最大3.5秒かかる。
  - すべての応手で詰めば続行。1つでも詰まなければ詰みを逃した。結論が出なければ（時間切れ・`none`）、今までどおり mini の `score mate` で決める。
  - 詰まない応手が見つかっても、mini の最善手が詰まない応手かを知るため、持ち時間の中で残りの応手も調べる。
  - 玉方の応手は mini の最善手。ただし詰みを逃したときに、mini の最善手が詰む応手なら、詰まないと分かった応手で応じる。猶予の長さは今までどおり mini の評価値で決める。
  - 詰み専用エンジンを読み込めなければ、mini だけで判定する（コンソールにエラーを出す）。
  - ヘッドレス Chrome で、2つのエンジンを同時に読み込めること（約400ms）と、3・7・11手詰の7問を収録解どおりに指して続くことを確かめた。
